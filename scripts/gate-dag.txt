# scripts/gate-dag.txt: the rows of the judge, one per line (CI-F3, D-F3a, D-F3b, CI-F3.3b-2).
# <idx> <id> <deps> <recursos> <clase> <cpu> <ram_gb> <dur_s> <orden…>
# idx: the serial order of the judge, multiples of 10; merge-gate.sh runs the rows in it. deps: ids of this table, or '-'.
# recursos: target:T, cluster:C, models, reader, comma separated, or '-'. clase: normal, exclusive, boundary or untimed.
# reader (CI-F3.4, D-F34g): the row builds nothing in its target, it runs the binary or the test binaries the target's
# producer built, so it waits for that producer (a row that is not a reader, above it) and shares the target with the
# other readers. The planner judges the table before it starts (D-F34f): one cluster per row, rows in one target ordered
# by their deps unless both are readers, a reader with its producer above it, and no other kind of resource.
# untimed (CI-F3.3b-2): the row schedules as normal, but its output is past the boundary line the judge of the test
# times reads up to (the planner prints the line before the first untimed block): only CV and M are untimed.
# criterio de cpu y ram: the most cpu and ram that the lanes of a row ask for in merge-gate.sh (cpu of the heaviest
# lane of its chain, from the table before CI-F3.3b-2; P, DC, CV and M take the figures of the steps they run).
# dur_s: the starting duration of a row without history (ci-rapido-F3.spec.md, F3.3b-1b-ii); with history the planner
# takes the median of its last runs.
# The order of a row is its step: `bash scripts/merge-gate.sh --step <id>`, and merge-gate.sh step_<id>() holds the work.
10 P - - normal 2 2 20 bash scripts/merge-gate.sh --step P
# CI-F3.3c (D-F3j, D-F3l, D-F3m): the leading NAME=value tokens are the step's environment. Each row that builds names its
# CARGO_BUILD_JOBS, so a step asks for its own share of the cores and not nproc. A row with models names the three ORT
# pools with the values of the plan of production on this machine (4, 4, 8; CI-F3.4, D-F34a: the plan gives the reranker
# 8, and the 2 of rerank.rs is only what a binary without a plan asks for when it wants the GPU); E2E names none, because
# there the plan decides, and the planner holds it against these (D-F34b). The cpu column is the most the row asks for: its
# jobs or its widest pool, since the phases of a row do not run at once. NLI is exclusive: it asserts a clock
# (nli_entailment, < 500 ms). Its tests open no database, but run-all-tests needs the judge's server (CI-J12), so it names a cluster.
# CI-K4 (D-K4a, D-K4b, D-K4c, D-K4d, D-K4e, D-K4f): the rows that compile in the dev profile (DBG, NLI, DC; `test` inherits from
# `dev`, so the tokens are DEV and never TEST) build with no incremental state, no debuginfo and with their symbols stripped:
# the profile is in the hash of every unit, so it is written here, once, and a reader (NLI) names exactly the tokens of the
# row that builds its target (DBG). The release rows (B3, REL, E2E) already build with debug = false and strip = true, and CV
# and M have a seed and an instrumentation of their own that a profile of the table would move: they name none.
