# 0.29 — Windows native, and `/health` that says where a model ran

Opened 2026-10-12 from the first native run on Windows since the gate moved to WSL2
(2026-10-03). Windows 11, RTX 4070 Ti 12 GB, Docker Desktop + WSL2 with
`networkingMode=mirrored`. 0.28.0 is published (`v0.28.0` = `57496c7`); this branch is
`feat/0.29`, cut from it.

## Found on the first Windows run (measured, not guessed)

- **`/health` reported a GPU reranker that ran on the CPU.** With the CUDA 12 runtime missing
  (`cublasLt64_12.dll`), ORT registration failed, `gpu.rs` logged `ERROR … esta sesión corre en
  CPU` and went on, and `/health` answered `reranker: {device: gpu, state: loaded}` and
  `gpu.degraded: false`. `http.rs::device_of` reads the *plan* (`gpu::wants_gpu`), not where the
  session opened. The 0.27 promise — "`/health` answers where the reranker runs" — holds only on
  a machine where nothing goes wrong, which is the machine that does not need it.
- **`merge-gate.sh` is married to `:5488`.** `pg_isready -h 127.0.0.1 -p 5488` is written out
  next to a `DATABASE_URL` the operator may override. With WSL2 mirrored networking the
  `localhost:5488` of Windows *is* the WSL Postgres (the live corpus, `172.30.0.5`), while the
  Docker Desktop container of Windows could not publish the port at all. A gate started on
  Windows would have judged — and created `brain_gate` on — the other host's server. The gate
  lock is per host, so it would not have noticed the other gate either.
- **The Windows prerequisites are written nowhere.** `docs/gate.md` has "Running the gate on
  Linux" and no Windows counterpart: the CUDA 12 + cuDNN 9 DLLs on `PATH` (the product only
  prints a note), the Postgres on its own port when WSL2 is mirrored, the container name the
  command guard demands.

## Slices

- **W1 — `/health` names the device the session opened on.** The placement record is written
  where the session is built (the three sites of `gpu.rs`/`onnx.rs`/`rerank.rs`/`nli.rs`), with
  the provider's cause, redacted of paths like the rest of `reason`; `/health` and `doctor` read
  it. A fallback is `device: cpu` with a reason, and `gpu.degraded` follows it.
- **W2 — the gate reads its Postgres from `DATABASE_URL`.** Host, port, user and database of the
  readiness check come from the URL the rest of the gate already uses; the `OK  Postgres :<port>`
  line stays the first line after the check. A URL the gate cannot parse is exit 2, not a guess.
- **W3 — `docs/gate.md`: Running the gate on Windows.** Prerequisites, the mirrored-network
  collision with WSL2 and how to tell which server answers, the receipt living in each host's own
  `~/.cache/cuba-gate`.

- **W4 — the gate's own contracts hold on Windows.** `local_gate_contract` was 36 passed / 2
  failed on native Windows since the Linux commits of 2026-10-03: a path compared as a string
  (`/` against `\`), and the self-test's `env/bare` built with `ln -s`, which Git Bash turns into
  a copy of an MSYS `.exe` that cannot load `msys-2.0.dll`.
- **W5 — a CUDA session with no published ceiling uses the card.** `cuda_provider` fell back to a
  fixed 2048 MB when nobody had called `resources::apply` (only `main` does); the reranker weighs
  4,23 GiB. `v017_rerank_gpu`'s two ignored tests were red on any machine with a card, and a
  CPU-only judge could not see it. The constant is gone.

## Open, carried (not this release)

Found by the review of the 0.29 diff (read-only, no critical finding), judged not blocking:

- `mode.rs::rerank_gpu_active()` caches `gpu::status().degraded` in a `OnceLock` on its first
  call. With `CUBA_WARM_RERANKER=0`, or a search that lands during the warm-up, that call happens
  before the placement registry has anything in it, and a reranker that later opens on the CPU
  still gets `rerank_default() == true` (60–110 s a search) while `/health` says degraded. The
  default eager warm-up fills the registry first, so the default path is right.
- The readiness fallback of `merge-gate.sh` without `pg_isready` on `PATH` still judges the
  container `memory-industry-db` by name (documented in `docs/gate.md`).
- `gpu::configure` records before `commit_from_file`: a commit that fails leaves a placement for a
  session that never existed. `/health` shows `failed` with `device: null`, so only `gpu::status()`
  can over-report; and `reranker_state`/`nli_state` read the registry and the cell in three
  steps, so one poll can show `loaded` with `device: null`.
- A DirectML-only build registers without `error_on_failure`, so a provider that ORT degrades in
  silence would be recorded as `Gpu`. The Windows release is built with `cuda,directml`; CUDA rules.
- `CUBA_EMBED_DEVICE=gpu` or `CUBA_NLI_DEVICE=gpu` with a plan that did not admit the reranker on
  the GPU now runs its CUDA session with no ceiling (it was 2048 MB); `SameAsRequested` grows only
  what is asked.
