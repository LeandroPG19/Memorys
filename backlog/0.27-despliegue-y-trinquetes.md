# 0.27 — deployment and ratchets

Opened from `INFORME-TECNICO-MCP.md`, the write-up of the first LAN deployment at a
company: Windows, an RTX 5050 with 8 GB, a daemon on `192.168.128.18:8787` serving
several machines. The report reads as a success. Held against this repository it was
not: none of its five fixes existed here, its diagnosis of the root cause was wrong,
and one of its patches turned an honest `fail` into a false `ok`.

The premise of this branch: installing this on a new machine should be a command that
either works or says why, and the gate should make these defects unable to return.

## Done

### The GPU works, or says why it does not

- The CUDA arena ceiling follows the card. It was `DEFAULT_GPU_MEM_LIMIT_MB` (2048)
  applied with `.min()`, so it was 2048 on every machine ever, and
  `bge-reranker-v2-m3` does not fit in 2048. **Every GPU install failed the same way**
  until somebody overrode it by hand. Now the ceiling is all free VRAM minus the
  reserve, and what the model needs is *measured from the file on disk* — 614 KB of
  graph plus 4.23 GiB of `model.onnx_data` on this machine — to decide whether it goes
  on the card at all, and with which chunk.
- A ceiling set below the measured floor is raised, with an `ERROR` naming both
  numbers. The company's launcher pinned `CUBA_GPU_MEM_LIMIT_MB=2048` and
  `set_if_absent` meant the measured plan never applied. Every other knob still yields
  to the operator; a floor the model demonstrably cannot load under is not a knob.
- The plan says the device where the session reads it (`CUBA_RERANK_DEVICE`, in both
  directions). Side effect worth having: `mode::rerank_default()` derives from the
  same flag, so reranking stops switching itself on where it costs 60–110 s per search.
- A CUDA provider that will not start is an error, not a line in the log. Two failure
  sites, and the report had only seen the second: EP registration (ORT degraded to CPU
  silently — `error_on_failure()` defaults to `false`) and session commit. Registration
  failure now drops to CPU **loudly**; commit failure stays hard. And the
  `sesión ONNX en GPU` line moved *after* a successful registration, which is why the
  company's log said GPU while the work may well have been on the CPU.
- The sentinel that disables the reranker disables it. Two path-resolution rules
  disagreed, and the one behind `get_status()` filtered on `.exists()` — the sentinel
  does not exist, so it fell through to the cache, which *does* have the model. The
  plan switched the reranker off, `doctor` said "no RAM", and the first search loaded
  it anyway.
- A search that asked for reranking and did not get it says so, with a different
  reason per cause. `reranker_degraded` used to be emitted only on timeout or
  inference error, never on the commonest case of all: no model.
- One budget that covers the load, not just the inference; the permit is taken with a
  timeout and released at the next chunk boundary. Resolving the model now happens
  *before* the permit is taken — holding the single permit across a 4.3 GB read made
  one search report "busy" while another was still reading.

### The daemon tells the truth

- The port is announced once the models are warm. It used to bind, announce, spawn the
  warm-up detached and serve — so the announcement was a lie and the first search paid
  for the load. Binding still happens first, which keeps the cheap diagnosis: a second
  daemon fails fast instead of spending two minutes loading before it finds out.
- `doctor --deep` loads what its help text says it loads. It only ever reached the NLI,
  and it called `nli::enabled()` straight from async — a live regression of `4d5dd76`,
  a gigabyte on the executor. Now `spawn_blocking` with a budget, and a timeout is a
  `fail` with the cause, never a skip and never a hang.
- `generative_llm` cannot go green on something it did not test. **The report's patch
  was deliberately not ported**: under the HTTP daemon `CLIENT_SUPPORTS_SAMPLING` is
  never set by design and `request_sampling_max` needs the stdio channel HTTP does not
  have. Reporting `OK — mcp_sampling` there is exactly the false green the repo bans.
- The port check reports real collisions instead of asserting that `:8788` is Cursor's
  OAuth callback — one workstation's fact, and backwards on the machine this ships to.

### The LAN

- Two machines stop sharing one session. `bind_key` did not look at origin, so two PCs
  with the same `Mcp-Client-Id` and no `Mcp-Session-Id` shared a jornada and a root
  project. That was not a risk; it was happening. Loopback stays a single bucket, so
  every key on every existing install is byte-identical to before.
- `/health` stops handing an anonymous caller the whole `graph_db`, `last_error`
  included — and a `last_error` can carry a host and a port.
- A token shorter than 32 characters is refused on a bind other machines can reach.
- The panel is not published on a routable bind, and a page from somewhere else cannot
  drive the daemon. `came_through_a_proxy` only caught proxies, and a LAN bind is not a
  proxy: with `CUBA_PANEL=1` the panel was open to the whole network. Origin is checked
  against an allowlist, and **no CORS headers are emitted** — a permissive
  `tower-http::cors` would *remove* the preflight protection that exists today, so
  there is a ratchet against the future commit that "fixes CORS".
- A wrong token is not free to retry (10 failures per 60 s per address, then 429;
  successful calls are never rate-limited), and `/health` cannot hang.

### The gate

- The second judge can judge a branch. `quality-gate.sh` had no way to look at one, so
  its mutation step exited 0 over nothing. It now takes `QG_BASE`, and lizard lost its
  `|| true` and gained a threshold, with a baseline so touching a pre-existing CC-30
  function does not fail the branch that touched it.
- `codigo-muerto.sh` could not fail: `has_discovery=1` made every file `continue`
  before the counter, so `orphans` was 0 by construction. It now checks the exclusion
  lists — excluded *there* must mean covered *here* — and `--self-test` builds a tree
  with an orphan in it and asserts the scan is non-zero. A verifier that cannot fail is
  a paragraph.
- `#[ignore]` has a two-way ceiling (144, of which 142 without a reason), counted from
  anchored attributes rather than mentions of the word.
- `quality-gate.ps1` is a wrapper around the `.sh`, not a second opinion. Two judges
  with different exclusion lists are two judges, and the Windows one runs where the
  product gets installed.
- Mutation stops poisoning the target directory the rest of the run builds in. This one
  cost four red tests on files nobody had touched; `quality-gate.sh` already knew and
  `mutants-gate.sh` never did.
- Build and mutation parallelism are derived from the machine instead of hand-tuned.
- Two tests that were green by accident now state contracts:
  `!Mode::Local.rerank_default()` was true only because CI compiles without cuda, while
  the release matrix ships Windows *with* it — the machine at the company is that
  build. And the OOD fit test measured wall-clock instead of asserting the fit does not
  run on the runtime worker.

### What the operator copies

- `.env.example` offers the GPU, daemon and LAN blocks, with defaults taken from the
  unit files and the source, not invented. Two contracts hold it there: every variable
  on the computed deployment surface must be offered, and every `Environment=` in
  `packaging/` must appear in it. The drift was never README ↔ code — that contract
  already worked. It was README ↔ the file people actually copy.
- `docs/despliegue-lan.md`, plus the `.gitignore` exception without which it would have
  been committed nowhere at all (`docs/*` with a single `!docs/gate.md`).

## Open

- **F2 — the versioned installer** (`setup service --print/--apply/--uninstall`,
  `service.rs`, golden files under `packaging/`, `packaging_contract.rs`). In progress.
  This is what answers "other people will install this in more places". Two defects it
  must fix are already confirmed in the shipped unit: `packaging/cuba-memorys.service`
  hard-codes `CUBA_GPU_MEM_LIMIT_MB=2048` — the report's bug, in git — and its
  `Documentation=` points at `github.com/LeandroPG19/cuba-memorys`, which does not
  exist. It also has to close a gap nothing here covers: this binary does not read a
  `.env` file (there is no dotenv crate) and Task Scheduler cannot set an environment
  variable, which is exactly why the first deployment grew a hand-written `.ps1` and an
  `.env` beside it that nothing ever loaded.
- **F4 — migrate the company machine** from the fixed repo, retiring the two hand-written
  `.ps1` and the orphaned `.env`. Only with the gate green, and with the negative
  control run *on that machine*: with `MEMORY_INDUSTRY_GPU_MEM_LIMIT_MB=512`,
  `doctor --deep` must fail citing the ORT arena, a rerank must come back
  `reranker_degraded` with the EP's cause, and `apply()` must have logged the raise.
  Today all three are silence, and that contrast is the proof the core landed.
- **R8 — TLS.** The token crosses the LAN in clear. Real, and out of scope on purpose:
  the fix is a project. For now, a long token and an honest paragraph in the guide.
- **The gate scripts should reject or absolutize a relative `CARGO_TARGET_DIR`.** Every
  cargo invocation in the gate runs after a `cd` into `rust/`, and cargo resolves that
  variable against each process's own directory — so a relative `rust/target-sil`
  lands in `rust/rust/target-sil`. It reached 11 GB before anyone noticed, and the
  anchored `.gitignore` patterns did not cover it. The patterns are fixed; the scripts
  are not.
- Retire `packaging/cuba-memorys.*` one release after the new units land, per
  `AGENTS.md`.
