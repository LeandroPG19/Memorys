## 0. Lo que el código ya hace (hechos medidos, de ellos cuelga el diseño)

- **Autenticación hoy**: `http::authorized(state, headers) -> Option<Scope>` es **síncrona**; compara `Authorization: Bearer …` con `CUBA_PEER_TOKEN` (→ `Scope::Peer`) y con `CUBA_HTTP_TOKEN` (→ `Scope::Full`) en tiempo constante (`same_secret`). Sin token configurado todo es `Full` (solo posible en loopback). Se llama desde `mcp_endpoint`, `events_ticket`, `authorized_events`, `health` (vista completa) y `panel`.
- **Freno**: `AppState.auth_failures` (por `IpAddr`), `MAX_AUTH_FAILURES = 10`, `AUTH_FAILURE_WINDOW = 60 s`; `brake_for` → 429 con `Retry-After`; un éxito limpia la dirección.
- **`/mcp` es `POST` y devuelve JSON** (`axum::Json`), nunca SSE; las notificaciones devuelven `202` vacío. `GET /events` es SSE (con ticket). El daemon no emite `Mcp-Session-Id` hoy, pero lo lee. `DefaultBodyLimit = 8 MiB`. Límites del router: `bound_every_request` (504 con texto propio).
- **Identidad de sesión**: `client_key` (cabecera `Mcp-Client-Id`, luego `_meta`, luego `clientInfo.name`), `request_origin` (`Origin::Local` si el par es loopback, si no `Origin::Remote(Mcp-Machine-Id | ip)`), `session::bind_key = client[@machine][::mcp_session]`. Las tareas locales (`with_scope`, `with_identity`, `with_root_project`) viajan por `tokio::task_local!` en `session.rs`.
- **Quién escribe qué hoy**: solo `current_client()` llega a `brain_handler_failures.client`, a `observability::Call.client`, a `artefacto` y a `centinela.from_agent`. `cuba_whoami` imprime `client_id`, `mcp_session`, `scope`. El audit (`brain_audit_log`) se escribe con `handlers::archivo::handle(pool, {"action":"append","event_action":…,"payload":…})`.
- **Pool y rol**: `db::create_pool` devuelve el pool de `cuba_app` (NOSUPERUSER, NOBYPASSRLS) en cuanto ese rol puede entrar; **la CLI y el daemon usan ese mismo pool**. `ALTER DEFAULT PRIVILEGES` da SELECT/INSERT/UPDATE/DELETE a `cuba_app` sobre toda tabla nueva. RLS `tenant_isolation` es por `project_id` en las tablas de contenido; las tablas nuevas no son de contenido y no llevan RLS.
- **Migraciones**: última 0064. `migrations_contract` congela hasta **0060** (`FROZEN_THROUGH = 60`, SHA-384 de nombres+bytes): **0065 es libre y no toca el digest**. Prohíbe `CREATE TRIGGER` y `ADD CONSTRAINT` sin guarda (las restricciones dentro de `CREATE TABLE` no cuentan). Convención de tablas nuevas: prefijo `brain_`, `uuid DEFAULT gen_random_uuid()`, `GRANT … TO cuba_app`, `COMMENT ON TABLE`.
- **Dependencias ya presentes** (y por tanto sin crate nuevo): `sha2 0.10`, `hmac 0.12`, `hex 0.4`, `uuid 1` (con `v4`, que usa `getrandom 0.4.2` del SO), `reqwest 0.12` (`stream`, rustls), `axum 0.8`, `tokio`, `async-trait`, `serde_json`, `chrono`. **No hay** `ed25519`, `rand` directo ni `subtle` directo. `ring` y `rustls` están solo como transitivos (de `reqwest`/`sqlx`): `ring` NO se convierte en dependencia directa (decisión S-3).
- **`doc_contract`** exige fila en `README.md` y entrada en `.env.example` por cada variable `CUBA_*`/`MEMORY_INDUSTRY_*` que aparezca como literal en `rust/src`, y tiene una lista de variables «del SO» de longitud fija (`[(&str,&str); 11]`: HOME, USERPROFILE, LOCALAPPDATA, HOSTNAME, COMPUTERNAME, PATH, …). **Esta spec no añade ninguna variable del SO** (el principal para `icacls` sale de `whoami`, no de `USERNAME`).
- **`cli_contract`**: `COMMANDS` (hoy 26), `README` dice «26 CLI commands», cada comando de `COMMANDS` debe responder `--help` con código ≠ 2, sin tocar PostgreSQL, imprimiendo una línea que empiece por `memory-industry <cmd>`; `main.rs` se recorre por brazos para exigir `drain` antes de `exit` en los que llegan a `handlers::`/`http::serve`/`protocol::run_mcp`/`drain_then_report` (los brazos nuevos siguen el patrón de `project`/`secure`, que no entran en esa lista).
- **Lizard**: `scripts/lizard-baseline.txt` guarda `ruta::función:línea CC`. Hoy están `http.rs::{mcp_endpoint:1135 13, dispatch_one:1276 12, serve_pool:191 11}`, `main.rs::async_main:127 24`, `doctor.rs::{run_checks_with:775 43, run_cli:1356 13}`, `setup_agent.rs::{run_check:154, run_write:274, run_hook:577, project_configs:24}`. Cualquier edición que mueva una de esas funciones cambia su clave.

### 1.2 Modelo de datos (migración **0065_accounts**, solo expand)

Convenciones de la guía `pg-aiguide`: `TIMESTAMPTZ`, `TEXT` + `CHECK`, `BYTEA`, **índice manual en cada FK**, acción `ON DELETE` explícita, `UUID` solo donde la opacidad importa (`gen_random_uuid()`, es v4 aleatorio: **no** `uuidv7()` aquí, porque el id de credencial va en el portador y no debe ser adivinable por tiempo).

```sql
CREATE TABLE IF NOT EXISTS brain_host_identity (
    singleton  boolean     PRIMARY KEY DEFAULT true CHECK (singleton),
    host_id    uuid        NOT NULL DEFAULT gen_random_uuid(),
    created_at timestamptz NOT NULL DEFAULT now()
);
INSERT INTO brain_host_identity DEFAULT VALUES ON CONFLICT DO NOTHING;   -- una fila, estable al repetir

CREATE TABLE IF NOT EXISTS brain_accounts (
    id         uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    name       text        NOT NULL CHECK (name ~ '^[a-z0-9][a-z0-9._-]{0,31}$'),
    created_at timestamptz NOT NULL,
    revoked_at timestamptz,
    CONSTRAINT brain_accounts_name_key UNIQUE (name)
);

CREATE TABLE IF NOT EXISTS brain_account_credentials (
    id           uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    account_id   uuid        NOT NULL REFERENCES brain_accounts(id) ON DELETE RESTRICT,
    device_label text        NOT NULL CHECK (device_label ~ '^[A-Za-z0-9][A-Za-z0-9._ -]{0,39}$'),
    secret_hash  bytea       NOT NULL CHECK (octet_length(secret_hash) = 32),
    created_at   timestamptz NOT NULL,
    last_seen_at timestamptz,
    revoked_at   timestamptz
);
CREATE INDEX IF NOT EXISTS idx_brain_account_credentials_account ON brain_account_credentials (account_id);

CREATE TABLE IF NOT EXISTS brain_pairing_codes (
    id            uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    account_id    uuid        NOT NULL REFERENCES brain_accounts(id) ON DELETE CASCADE,
    code_key      bytea       NOT NULL CHECK (octet_length(code_key) = 32),
    device_label  text        CHECK (device_label ~ '^[A-Za-z0-9][A-Za-z0-9._ -]{0,39}$'),
    created_at    timestamptz NOT NULL,
    expires_at    timestamptz NOT NULL,
    used_at       timestamptz,
    credential_id uuid        REFERENCES brain_account_credentials(id) ON DELETE RESTRICT,
    CHECK (expires_at > created_at AND expires_at - created_at <= interval '24 hours'),
    CHECK ((used_at IS NULL) = (credential_id IS NULL))
);
CREATE INDEX IF NOT EXISTS idx_brain_pairing_codes_account ON brain_pairing_codes (account_id);
CREATE INDEX IF NOT EXISTS idx_brain_pairing_codes_credential ON brain_pairing_codes (credential_id);

ALTER TABLE brain_handler_failures ADD COLUMN IF NOT EXISTS account text;
-- privilegios: los de omisión de cuba_app, menos DELETE donde borrar sería borrar historia
REVOKE DELETE ON brain_accounts, brain_account_credentials, brain_host_identity FROM cuba_app;
COMMENT ON TABLE … (una por tabla: qué guarda y qué NO: «nunca el secreto ni el código»).
```
`created_at`/`expires_at` **sin DEFAULT** en cuentas, credenciales y códigos: el reloj lo pone el llamador (inyectable); un DEFAULT escondería un reloj sin inyectar. `.down.sql`: `DROP TABLE IF EXISTS` en orden inverso + `ALTER TABLE brain_handler_failures DROP COLUMN IF EXISTS account`. Sin `CREATE TRIGGER` ni `ADD CONSTRAINT` fuera de `CREATE TABLE` (el contrato de migraciones lo exige). **Por qué SHA-256 y no una KDF lenta**: el secreto tiene 256 bits de entropía aleatoria; una KDF lenta (argon2/bcrypt) protege contraseñas de baja entropía y aquí solo encarecería cada petición sin subir la seguridad. El código de emparejamiento (60 bits) se guarda como `code_key` (SHA-256 con dominio) porque el servidor necesita una clave HMAC derivada del código para probar que lo conoce (S-9); caduca en 24 h y se invalida al usarse.

### 1.3 Diseño de identidad (cerrado: simétrico, sin crate nuevo)

| # | Decisión | Por qué | Cómo se revierte |
|---|---|---|---|
| S-9 | **Identidad simétrica con HMAC-SHA256, sin criptografía de clave pública y sin dependencias nuevas.** Candidatas evaluadas: (1) par ed25519 persistente de la madre + huella en el código: necesita `ed25519-dalek` (MIT/Apache) o hacer directa `ring` (ya transitiva); en ambos casos `socket depscore` + `osv` antes, y una clave privada que custodiar en la base; (2) HMAC con secretos que ya existen. Cierro la (2): el código de emparejamiento (conocido solo por quien lo imprime y quien lo teclea) prueba la identidad **durante el emparejamiento**, y el **hash de la credencial** (que solo conocen la madre y el dispositivo) la prueba **después**. Un impostor no puede fabricar ninguna de las dos pruebas porque no tiene ninguno de los dos secretos. | Cero superficie nueva de cadena de suministro; la huella en el código no hace falta porque el código mismo es la prueba. | Cambiar `identity_proof` y `pair_response_mac` por firmas ed25519 cuando llegue TLS (S-12); el protocolo es `v:1` y la versión viaja en el JSON. |
| S-10 | **La credencial la genera el CLIENTE** (32 bytes), y **jamás viaja**: en el emparejamiento solo se envía `h = SHA-256(secreto)` autenticado con el HMAC del código. La madre devuelve el `credential_id`. El portador posterior es `mi1.<credential_id: 32 hex>.<secreto: 64 hex>`. Consecuencia: un espía pasivo del emparejamiento (o un impostor que recibe esa petición) no obtiene nada utilizable, y romper el código por fuerza bruta offline después no revela la credencial. | Cierra el hueco de «entregar el secreto a quien responda». | Que la madre genere y devuelva el secreto: invierte S-10 y obliga a enmascararlo con el código. |
| S-11 | **Entropía sin crate nuevo**: `uuid::Uuid::new_v4()` ya usa el CSPRNG del SO (`getrandom`). `random_bytes(n)` concatena `n.div_ceil(16)+1` UUID v4 y los pasa por SHA-256 (366 bits de entropía real en la entrada para una salida de 256). El código se saca de `SHA-256(u1‖u2)` tomando 60 bits. | Evita añadir `getrandom` como dependencia directa (la alternativa válida: es el mismo `getrandom 0.4.2` que ya tiene `uuid`, el lock ganaría una arista y ningún crate). | Hacer directa `getrandom = "0.4"` y llenar el buffer sin blanqueado. |
| S-12 | **TLS NO entra en 0.29.0** (es la siguiente versión). Límites honestos que la guía y `doctor` dicen: el tráfico sigue en HTTP en claro; la prueba de identidad **frena** a quien contesta en una dirección sin conocer el secreto (host equivocado, nombre resuelto por un envenenador de LLMNR/NetBIOS, un equipo que heredó la IP por DHCP, un barrido que topa con otro servidor), pero **un atacante activo en el camino** (ARP spoofing) puede retransmitir la prueba a la madre real y quedarse con el portador, y **un espía pasivo** lee el portador igual que lee hoy el token compartido. La mitigación disponible ya: cada dispositivo tiene su credencial revocable de inmediato (el token compartido no). | Lo que no se puede cerrar sin TLS se dice. | — (TLS es la solución). |
| S-13 | **Frescura de la verificación en el puente**: antes de la primera petición, y de nuevo si pasaron más de `REVERIFY_AFTER = 30 s` desde la última prueba válida o tras cualquier error de transporte. Mientras tanto se reutiliza la dirección verificada. | Una dirección que cambia de dueño (DHCP) recibiría credenciales como mucho 30 s. | Subir/bajar la constante. |

### M2 · QA manual en la madre real y en un segundo PC Windows — NO AUTOMATIZABLE

Es el último escenario: nada de lo de arriba prueba Windows, `schtasks` por usuario, la consola oculta, el firewall, el barrido de una LAN real ni un cambio de IP de verdad. Lo hace una persona (o Playwright/otro agente con acceso a esas PC) y se anota la salida literal en el handoff de QA. Requiere haber pasado antes M1 (el servicio de la madre ya existe).

```gherkin
  Escenario M2 (manual): emparejar en menos de dos minutos, sobrevivir a reinicios y a un cambio de IP, revocar y rechazar a un impostor
    Dado la madre con el servicio 0.29.0 en 192.168.0.10:8787 (perfil lan), un segundo PC Windows en la misma subred, y un tercer equipo cualquiera para hacer de impostor
    Cuando se siguen los pasos 1 a 12
    Entonces cada «Entonces» de cada paso se cumple
```

1. **IP fija.** En PowerShell elevado de la madre, siguiendo la guía (`Get-NetIPConfiguration`, `Set-NetIPInterface … -Dhcp Disabled`, `New-NetIPAddress`, `Set-DnsClientServerAddress`). Ejecutarlo con la consola física (no por RDP: se corta la red). Esperado: `ipconfig /all` muestra «DHCP habilitado: no» y la dirección elegida; tras reiniciar la madre sigue igual y el servicio responde. **No verificado**: la secuencia exacta de cmdlets en una máquina real; se anota la salida literal y cualquier orden que hubo que cambiar.
2. **Cuenta y código.** En la madre: `memory-industry account add ana`; `memory-industry account pair ana --device pc-lab-1`. Esperado: sale un código `XXXX-XXXX-XXXX` (sin 0/O/1/I), la huella de 16 hex, «valid until» a 24 h; `account list` muestra a `ana` sin ningún secreto. Repetir `account pair` sin `--device` y comprobar que el cliente fija su etiqueta.
3. **Emparejar (cronómetro).** En el segundo PC, como usuario **estándar** (sin administrador), con `memory-industry.exe` copiado a `%LOCALAPPDATA%\MemoryIndustry\`: `memory-industry bridge pair <código>` **sin `--host`**. Esperado: termina en < 2 min contando el tecleo, imprime la huella y es IGUAL a la de la madre, la cuenta `ana`, la etiqueta `pc-lab-1`, la ruta de `bridge.json`; **no** imprime el secreto. `icacls %LOCALAPPDATA%\MemoryIndustry\bridge.json` muestra solo a ese usuario (sin herencia). Repetir con `--host 192.168.0.10` y con `--host <nombre de la madre>` (con un código nuevo cada vez): ambos valen. Volver a usar el MISMO código ya canjeado desde otro equipo: falla con el mensaje genérico.
4. **Puente y cliente.** `memory-industry bridge install` (sin administrador). Esperado: la tarea `MemoryIndustry Bridge` existe (`schtasks /Query /TN "MemoryIndustry Bridge"`); **no** aparece ninguna ventana de consola al iniciar sesión. **No verificado**: que un usuario estándar pueda crear `ONLOGON` y que `conhost.exe --headless` oculte la consola; si falla, el sustituto es `HKCU\…\Run` o `FreeConsole` (toca solo `install_commands()`). `memory-industry setup client claude --apply` y `… cursor --apply`. Esperado: `Select-String` de la IP de la madre y del secreto sobre `%USERPROFILE%\.claude.json` y `%USERPROFILE%\.cursor\mcp.json` no encuentra nada. En Claude Code y en Cursor, una llamada a `memory_whoami` devuelve `account: ana` y `device: pc-lab-1`. **No verificado**: que Cursor acepte `"type":"http"` junto a `url`; si no, se quita la clave `type` solo para Cursor.
5. **Reinicio del puente y del cliente.** Matar `memory-industry.exe` del cliente (`taskkill /F`), luego `schtasks /Run /TN "MemoryIndustry Bridge"`; después reiniciar el PC y volver a llamar. Esperado: funciona sin tocar ninguna configuración ni volver a emparejar.
6. **Cambio de dirección de la madre.** Cambiar la IP de la madre a otra de la misma /24 (y actualizar el servicio con `setup service --apply --profile lan --addr <nueva> --register`). Esperado: la primera llamada del cliente tras el cambio falla como mucho una vez con el mensaje que nombra lo probado (o se cura sola dentro de `discovery_total`); `memory-industry bridge doctor` lista los candidatos (última buena → guardadas → nombre → barrido) y marca verificada la nueva; `bridge.json` ya tiene `last_good` nuevo; la configuración del cliente no se tocó. Anotar los segundos que tardó.
7. **Revocar.** En la madre: `memory-industry account revoke-device ana pc-lab-1`. Esperado: la siguiente llamada del cliente falla con el mensaje de «revocada: empareja de nuevo»; `bridge doctor` lo dice; en el log del daemon no hay una avalancha de 401 (como mucho uno por minuto). Emitir un código nuevo y re-emparejar: vuelve a funcionar sin reiniciar el puente.
8. **Impostor.** Con la madre apagada, en el tercer equipo (o en el mismo cliente) asignar la antigua IP de la madre y dejar escuchando algo que muestre cada byte recibido en el puerto 8787 (por ejemplo `ncat -l -p 8787 | Tee-Object impostor.txt`, o un script que vuelque cabeceras). Esperado: el cliente recibe el rechazo del puente (no hay madre verificada) y `impostor.txt` NO contiene `Authorization`, `Bearer`, `mi1.` ni el cuerpo del `tools/call`; solo `GET /identity`. Con la madre real encendida de nuevo, el puente vuelve a entrar sin intervención.
9. **Huella cambiada.** Restaurar en la madre una base **distinta** (otro `host_id`) y reiniciar el servicio. Esperado: el cliente recibe el error con las dos huellas y «bridge pair»; `bridge.json` no cambió; `bridge doctor` marca `WrongHost`; tras emitir un código nuevo y `bridge pair`, vuelve a funcionar. Después restaurar la base original (mismo `host_id`, mismas credenciales): los clientes viejos vuelven a entrar SIN re-emparejar (la identidad viaja con la base).
10. **Perilla.** En la madre: `MEMORY_INDUSTRY_REQUIRE_ACCOUNTS=1` en el env file y reiniciar. Esperado: un cliente 0.28 con el token compartido recibe el texto exacto de rechazo; el cliente con puente sigue; `memory-industry doctor` pasa de warn a ok. Volver a `0` y comprobar que el token compartido vuelve a valer.
11. **Dos clientes a la vez** con la misma cuenta y etiquetas distintas: ambas llamadas se atribuyen a su `device`; revocar una no afecta a la otra.
12. **Lo que el QA no puede comprobar y lo dice**: caducidad real de 24 h (cubierta con reloj inyectado), barrido en una /24 con cientos de equipos (anotar el tiempo del `bridge doctor`).

Sabotajes manuales de M2: (a) dejar un servidor que mienta con el `host_id` correcto y sin prueba (el paso 8 ya lo hace) y comprobar que el puente no le envía nada; (b) borrar `bridge.json` y reiniciar el puente ⇒ `bridge run` sale ≠ 0 con «no está emparejado» y el cliente ve un error de conexión rechazada (no un cuelgue).

## 6. Modelo de amenazas (qué se defiende, cómo, y lo que NO)

| Amenaza | Defensa en 0.29.0 | Límite honesto |
|---|---|---|
| **Atacante en la LAN que suplanta una dirección** (otro equipo con la IP vieja de la madre, nombre envenenado por LLMNR/NetBIOS, un servidor cualquiera que contesta en el barrido) | El puente envía la credencial SOLO a un respondiente que superó `identity_proof` (HMAC keyed por el hash de la credencial) y cuyo `host_id` coincide con el fijado; H15/H16. En el emparejamiento, la respuesta lleva un MAC con `code_key`. | Un atacante **activo en el camino** (ARP spoofing) puede retransmitir la prueba a la madre real y quedarse con el portador. Solo TLS lo cierra (siguiente versión). |
| **Espía pasivo** | Cada dispositivo tiene su credencial revocable al momento. | El portador y todo el tráfico van en HTTP en claro, como el token compartido hoy. TLS: siguiente versión. |
| **Repetición** | El nonce de `/identity` es fresco por comprobación; repetir una petición de `/pair` es inocuo (idempotente, no entrega secreto). | Repetir el portador espiado = amenaza anterior. |
| **Fuerza bruta del código** | 60 bits; 10 fallos/min por dirección (freno compartido); 24 h de vida; un solo uso; ≤ 50 códigos activos. Probabilidad de acertar por código y día desde una dirección: 14 400 / 2^60 ≈ 1,2·10⁻¹⁴; desde las 254 de una /24 ≈ 3·10⁻¹²; contra los 50 códigos ≈ 1,6·10⁻¹⁰. Offline sobre un MAC espiado: 2^60 HMAC-SHA256 a un ritmo supuesto de 10⁹/s por GPU (**supuesto, no medido**) ≈ 36 GPU-años, y el código ya está gastado: lo que se obtendría es inútil porque la credencial no viaja (S-10). | El freno es por dirección: detrás de un NAT o del túnel de Cloudflare todo comparte cubo (por eso S-22 niega `/pair` a lo que trae cabeceras de proxy). |
| **Robo de la credencial del disco del cliente** | `bridge.json` con ACL de un solo usuario escrita ANTES del secreto, falla cerrado; nunca se imprime; revocable. | SYSTEM y los administradores locales pueden leerlo. Sin DPAPI en esta versión. |
| **Otro usuario del mismo PC cliente** | — | El puente escucha en loopback sin autenticación local: cualquier proceso de cualquier usuario del PC puede usar la credencial a través de él. Se asume un PC con un usuario. Autenticación local del puente: fuera. |
| **Una página web abierta en el cliente** | `browser_guard` (Origin y Host), H29. | — |
| **Dispositivo revocado que sigue intentándolo** | 401 en la siguiente petición; el puente deja de insistir al ver `revoked` en `/identity`; cuenta en el freno. | — |
| **Fuga de la base** | Solo hay `SHA-256(secreto)` y `code_key`; ninguna credencial es utilizable (preimagen de 256 bits). Un `code_key` vigente permite canjear ese código dentro de sus 24 h; el hash de una credencial permite suplantar a la madre ante ESE dispositivo (no entrar como él). | Las copias de `scripts/backup-db.sh` contienen todo esto: se protegen como la base. Restaurar una copia en otra máquina conserva `host_id` y credenciales, y por eso los clientes siguen entrando. |
| **Quien administra la madre** | Sus acciones quedan en la cadena de auditoría. | Quien ejecuta la CLI tiene acceso a la base y es la raíz de confianza. |

### Lo que deliberadamente NO está en esta versión

- **TLS** (siguiente versión; hasta entonces HTTP en claro y la advertencia de S-12). Firma por petición: descartada (se tiraría al llegar TLS).
- **Visibilidad por cuenta**, roles o permisos por cuenta, límites por cuenta (S-2). Todas las cuentas son `Full`.
- **Caducidad o rotación automática** de credenciales (S-8), cambio de nombre o borrado de cuentas, SSO/AD/LDAP.
- **DPAPI / almacén de credenciales del SO**, autenticación local del puente, cifrado del `bridge.json`.
- **Un MCP tool de cuentas** (S-3); un panel web de cuentas.
- **Descubrimiento por mDNS o difusión UDP**, barrido de máscaras distintas de /24, IPv6 (otras subredes: por nombre o dirección guardada).
- **El puente como servicio de Windows** (es tarea por usuario), auditoría de la ACL en `bridge doctor`, actualización automática del binario cliente.
- **Clientes Linux/macOS** (el código es portable y compila, pero no se prueba ni se documenta).
- **Cuentas con el túnel de Cloudflare** (`/pair` y `/identity` se niegan a lo que trae cabeceras de proxy).
- **Un cambio en `setup check`**, ni en `Call.client`, `bind_key`, `current_client()`.

## 7. No verificado (cae en M2 o en una verificación del implementador)

1. Que un usuario estándar pueda crear una tarea `ONLOGON` con `schtasks /Create`, y que `conhost.exe --headless` oculte la consola (S-20).
2. La secuencia exacta de cmdlets de IP fija en una máquina real, y el comportamiento de `Set-NetIPInterface -Dhcp Disabled` / `New-NetIPAddress` con una puerta de enlace ya presente.
3. Que Cursor acepte `"type":"http"` en `mcp.json`.
4. Que `UdpSocket::connect` + `local_addr()` dé la interfaz correcta en Windows con varias interfaces (VPN, Docker/WSL); si falla, el barrido se omite y el informe lo dice.
5. Que el resolutor de Windows (`getaddrinfo` vía `tokio::net::lookup_host`) resuelva nombres de una sola etiqueta por NetBIOS/LLMNR en la red real.
6. La cifra de 10⁹ HMAC/s por GPU del modelo de amenazas (supuesto).
7. Que `ci-rapido.md` se cumple: ningún test de esta spec espera a la red real; los respondientes lentos son oyentes de loopback con tiempos diminutos inyectados (`Timing`). El implementador mide la duración de cada binario y la anota; el techo por binario del juez manda.
8. Dependencias nuevas: **ninguna** (S-9, S-11). Si el implementador discrepa y quiere `getrandom` directo o un crate de firmas, DEBE parar y devolver una nota: antes de añadirlo hay que correr `socket depscore` y `osv` (regla global) y hablarlo, y `deny.toml` solo admite licencias MIT/Apache/BSD/ISC/CC0/Zlib/Unicode/OpenSSL/CDLA.
9. No consulté `memory-industry` (el MCP no está disponible para este subagente): el orquestador debería guardar el decreto de S-9/S-10 (identidad simétrica con credencial generada por el cliente).
